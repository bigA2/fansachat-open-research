## Risk classes (as the sources define them) and what they mean for a workflow builder

| class | source definition (quoted or short) | where it hits FansaChat |
|---|---|---|
| Direct injection | "occur when a user's prompt input directly alters the behavior of the model in unintended or unexpected ways" (LLM01) | the one-sentence request typed into the builder |
| Indirect injection | "occur when an LLM accepts input from external sources, such as websites or files" (LLM01) | app data read by AI steps at run time (emails, tickets, form answers, file names, feed items) and sample data shown to the builder |
| Obfuscation / encoding | Base64, hex, "Unicode smuggling with invisible characters", scrambled spelling (Cheat Sheet, "Encoding and Obfuscation", "Typoglycemia") | filters based on keywords miss these; normalise text before checks |
| Multilingual / multimodal | LLM01 scenarios "Multilingual/Obfuscated Attack" and "Multimodal Injection" | requests in other languages, text hidden in images or PDFs |
| Role-play / jailbreak | Cheat Sheet "Jailbreaking Techniques", "Multi-Turn and Persistent Attacks" | long chats with the builder |
| System prompt leakage | system prompts "may inadvertently contain secrets" (LLM07) | the builder prompt; keep secrets and keys out of it |
| Excessive agency | "damaging actions ... in response to unexpected, ambiguous or manipulated outputs", triggered by "excessive functionality; excessive permissions; excessive autonomy" (LLM06) | AI steps that can call any connected app or run without approval |
| Improper output handling | "insufficient validation, sanitization, and handling of the outputs generated by large language models before they are passed downstream" (LLM05) | builder JSON going to the engine; AI step text going into emails, sheets, HTML, webhooks |
| Unbounded consumption / denial of wallet | "excessive and uncontrolled inferences"; denial of wallet exploits "the cost-per-use model of cloud-based AI services" (LLM10) | very long inputs, AI steps in tight loops, high-frequency schedules |
| Data exfiltration | "Attempts to extract API keys, passwords, or system information" (Cheat Sheet) | connection tokens, other users' data |

## Defences to build (from the Cheat Sheet and OWASP pages)

1. **Treat app data as data.** Keep instructions and untrusted content clearly separated in AI-step prompts (Cheat
   Sheet: "Structured Prompts with Clear Separation"; "Remote Content Sanitization").
2. **Validate the builder's output against a strict schema.** Only known step types and catalog apps; reject unknown
   fields; cap steps per workflow (see `results/TIER_AUDIT.md`). This is LLM05 for our own JSON.
3. **Least privilege per workflow** (Cheat Sheet "Least Privilege"; LLM06): a workflow uses only the connections it was
   built with. An AI step cannot call apps that were not in the approved plan.
4. **Human approval for actions with outside effects** (Cheat Sheet "Human-in-the-Loop"): sending to new recipients,
   deleting, paying, sharing publicly. Lindy does the same: anything with outside impact "waits for approval"
   (https://www.lindy.ai/pricing).
5. **Normalise input before checks:** Unicode normalisation, strip zero-width and direction-control characters, decode
   obvious encodings, flag mixed scripts in app names.
6. **No secrets in the system prompt** (LLM07). Keys live in the engine's secret store, never in model context.
7. **Budgets** (LLM10): maximum input length, AI steps per run, run frequency, and a per-account daily AI spend cap that
   pauses and alerts.
8. **Escape AI output** wherever it is shown or forwarded (HTML, Markdown, spreadsheet formulas, URLs) (LLM05).
9. **Monitoring** (Cheat Sheet "Comprehensive Monitoring"): log builder refusals and blocked steps; review samples weekly.
10. **No defence is complete.** Simon Willison's series argues for limiting the blast radius rather than trusting
    filters (https://simonwillison.net/2023/Dec/20/mitigate-prompt-injection/).
